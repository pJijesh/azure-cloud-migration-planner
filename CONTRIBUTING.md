# Contributing

Thanks for taking an interest. Issues and pull requests are welcome, especially corrections to rules, documentation and anything that is factually wrong.

## Ground rules

- **Everything in the examples stays fictional.** Do not add names, systems, prices or figures from a real organisation or a real quote. The example cost numbers are placeholders and must stay clearly labelled as illustrative.
- **No live prices.** The tool contains no Azure price data and should not. Cost inputs come from the user.
- **Check and cite facts.** For any statement about Microsoft guidance, product names, support dates or limits, say in the pull request what you checked it against and when. Paraphrase. Do not paste text from vendor documents, standards or books.
- **Rules are judgement, so keep them readable.** Every rule needs a plain-English reason that makes sense to an application owner. Do not add a rule you cannot explain in one sentence.
- **Standard library only.** The package has no runtime dependencies. pytest is the only development dependency.
- **British English**, plain and professional, no hype. Do not use dashes as punctuation (use commas, colons, full stops or brackets).
- **Be honest about limits.** Do not word anything as if the tool replaces Azure Migrate, a vendor quote or the judgement of application owners.

## Setting up and running the checks

```bash
python -m pip install -e ".[dev]"
python -m pytest -q
python tools/build_docs.py --check
```

If you change a rule in `migration_planner/default_rules.json`, regenerate the rule table and the checklist page with `python tools/build_docs.py`, and regenerate the example output:

```bash
python -m migration_planner plan examples/inventory.csv \
  --assumptions examples/cost-assumptions.json --as-of 2026-11-11 --out examples/output
```

A test compares `examples/output/` with a fresh run, so a change to rules or code that alters the example must be committed together with the new output. Check the difference reads sensibly before you commit it.

## Diagrams

Diagram sources are Mermaid files in `docs/diagrams/`. After editing one, render it with Mermaid CLI (`mmdc -i name.mmd -o name.svg`, and a `.png` for the README) and look at the result to check it is legible. The wave example is generated by the tool itself from `docs/diagrams/wave-example.csv`.

## Changing the model

- Add or change tests with known expected values. For cost changes, include a hand calculation in the test, as `tests/test_cost.py` does.
- Keep output deterministic: sorted, no timestamps, no absolute paths.
- Bad input must produce a readable error that names the file, line and value, and exit status 2.

## Pull requests

Keep them small and explain what changed and how you tested it. State plainly what you could not test.
